# 功能介绍、规划与继续

这里定义用户入口与流程的完成条件。制作 / 检查 / 验收的证据规则见 [acceptance.md](acceptance.md)。流程名是自然语言参数，不是宿主新增命令。

## 知情式建议与决策

用户是产品决策者，AI 负责查资料、发现缺口、解释影响、提出建议和执行已授权事项。每次出现会改变玩法、数据、费用、公开效果、依赖或工作范围的选择时，必须把“建议”和“决定”分开。

### 决策状态

| 状态 | 含义 | AI 应如何处理 |
| --- | --- | --- |
| 用户已确定 | 用户直接要求或此前明确选择 | 原样保留；若与平台硬限制冲突，说明冲突并等待改选 |
| 推荐默认 | AI 认为当前最合适的方案 | 说明理由、收益、代价和可撤销性；标成推荐，不冒充用户决定 |
| 可选增强 | 能提升体验但不是当前玩法必需 | 说明适用场景和实现成本；不自动塞进本次范围 |
| 不建议 / 不适用 | 收益低、风险高、平台不支持或与玩法不匹配 | 说明原因并给轻量替代，不用贬低式话术施压 |
| 待用户决定 | 不同答案会实质改变结果，且上下文无法推断 | 一次只问最关键的问题；得到选择前不执行该分支的实质写入 |

低风险、可逆的排版细节、题材化空状态和内部命名可以在既有制作授权内补齐；如果用户说“你来定”或明确委托 AI 决定，可代选并在动手前简短披露采用了什么。下列事项不能靠默认值静默越过：核心玩法与胜负结构、是否一点即发、是否覆盖 / 删除 / 重置存档或会话、真实付费模型调用、引入外部服务或大型依赖、公开发布，以及明显扩大本次制作范围的功能。

### 如何给建议

对一个真正需要选择的问题，最多给 2～3 个互斥方案，并包含：

1. 当前事实或缺口，不能把未验证猜测写成事实。
2. 每个方案对玩家体验、手机适配、性能、数据安全或制作成本的主要影响。
3. 一个清楚标注的推荐及理由；允许用户拒绝、修改或稍后再做。
4. 用户不选择时保持什么现状；不能用“默认继续”暗中获得额外授权。

避免一次抛出十几个开关。优先呈现最多 3 个高价值决定，其余进入“以后可加”；用户要求完整方案时再展开全部清单。

### 现有项目的功能体检

当用户问“现在是否齐全”“还能优化什么”“需要添加什么”时，先核对文件、配置和真实界面，再按下面格式回答：

| 分组 | 必须说明 |
| --- | --- |
| 已具备 | 功能与证据，不把文档声明当成已实现 |
| 需要修复 | 已失败或阻断体验的问题、严重度和验证方式 |
| 建议优化 | 已能用但体验可明显改善的项目、收益与代价 |
| 可选增强 | 适用玩法、预期价值、额外复杂度和是否需要用户选择 |
| 不适用 / 平台限制 | 为什么不做、可以采用的替代方案 |
| 未验证 | 缺少的环境、授权或真实设备，不能写成通过 |

优先级使用：P0 阻断核心游玩或可能损坏数据；P1 明显影响多数玩家；P2 锦上添花。优先级只是建议顺序，不代表获得制作授权。把用户最终选择写进已有需求表、项目记录或版本化设置；后续只重提发生变化或仍未决定的项目，不让用户反复回答。

## 功能介绍

适用：用户问“有哪些功能”“怎么使用”，或只调用技能，没有具体任务。

用下面四组介绍能力，并给两三个与用户需求相关的调用示例；不要求先完成整张问卷。说明哪些是复杂舞台的推荐基线、哪些仅在对应玩法下加入、哪些需要用户选择，避免把能力菜单说成当前项目的承诺。

| 类别 | 应向用户说明 |
| --- | --- |
| 能制作 | 标签人设与开场白、独立世界书、正则美化 / HUD / 侧栏、完整 LLM 文字互动舞台 |
| 完整游戏默认考虑 | 开局视觉与布局信息收集、全中文、电脑 / 手机适配、可打开的设置、选项 + 自由输入、加载 / 错误反馈；选项默认进入游戏内部输入框 |
| 按玩法加入 | 长线进度的自动与多槽存档；任务、背包、装备、关系、地图、经营、回忆、声音或 3D。不是每张卡都需要 |
| 技术增强 | 复杂舞台可选 Vue 3；复杂动效、2D、3D、音频、富文本和大型状态校验再分别评估 Motion、PixiJS、Three.js、Howler、DOMPurify 与构建期 Ajv。外链需要固定版本、平台白名单实测和无依赖降级，不作为默认承诺 |
| 平台边界 | 游戏用 sdk.stage；宿主不擅自改布局；父层换肤看官方主题桥；公开交付不靠玩家安装扩展 |

这是一份**可提供的制作能力说明**，不是“当前项目已经全部实现”的声明。介绍现有卡的功能时必须先核对文件和实际界面。

首次新项目已有明确任务时，只简述适用默认项并执行。已有项目的追问不重复菜单。用户指定不需要某项时记录取舍；单个人设 / 单个按钮不强制加入设置、存档或复杂舞台。

可用开场示例（按任务缩短，不逐字背诵）：

> 我可以做角色人设、世界书、界面美化或完整文字游戏。完整游戏会考虑电脑 / 手机适配、阅读与行动设置；长期玩法加入自动和多槽存档。任务、背包、关系、地图按题材选择。你可以直接说需求，或者让我推荐功能和视觉方向；网站未开放的部分会提前注明。

用户只问功能，到介绍与调用示例结束；不要自动创建角色、写文件或导入网页。

## 规划

适用：用户要玩法 / 页面设计、视觉推荐或明确要求“先规划”。

1. 复用已知题材、用户提供的参考、现有卡和不可改要求。完整游戏读 [stage-game-brief.md](stage-game-brief.md)；新复杂项目的视觉信息不足且用户想自己决定时，发送其中已预填的“美化与布局需求表”。单个 HUD 只查对应配方。
2. 把方案分成“用户已确定”“推荐默认”“可选增强”“本次不做 / 不适用”和“待用户决定”。每个拟建页面说明数据从哪里来、玩家能做什么、无数据时显示什么，并写明主要收益和代价。不能用“有个背包按钮”代替背包页面设计。
3. 视觉推荐读 [ui-reference-sources.md](ui-reference-sources.md)，提供已核实的来源页与可借鉴内容。只有首页或链接打不开时不能声称已经看过里面的界面。
4. “你来决定 / 不确定”允许 AI 补齐设计：推荐一套与玩法一致的组合，简述理由。不把同一问卷再退给用户，也不自动加入所有可选功能。
5. 列明验证方式与关键平台限制。只问规划时停在方案；原请求已要求制作时，方案不必制造一次多余确认，可在既有授权内继续制作。

完成条件：主页面与承诺入口有清楚的结构、数据来源、交互和空状态；布局能解释为题材、核心循环与信息优先级的结果，而非通用模板换皮；用户决定、推荐、可选、不做与待定已经区分；重大未决选择或平台限制已说明，AI 没有把建议冒充成授权。

## 制作与检查如何接续

- 制作：进入主文档制作流程，按实际需求加载参考。已存在的项目先读记录和对应源码，优先复用构建器、解析器和测试。
- 检查：先定复现方式，收集证据，再给出原因 / 缺项 / 建议。发现问题不等于获得修复授权。
- 验收：逐项对应本次需求，报告实际结果；失败项保留为失败，不通过偷偷删需求、改测试预期来通过。
- “检查并修好”包含修复；“看看是不是网站问题”只包含诊断。按整个直接请求判断，不机械匹配一个关键词。
- 两类请求混合时，可以分段处理，但分别守住只读与写入边界。

## 继续

适用：用户说“继续”“继续未完成项”。

按下列顺序恢复上下文，不重新全盘搜索或重跑已完成的流程：

1. 读取当前项目已有 README、交付记录或待办，确认源码、生成物、技能位置、实际目标站和版本；不假设上次的域名 / 角色 ID 仍然有效。
2. 核对与本次任务有关的文件、测试结果和当前页面状态。历史记录是恢复线索，不是今天仍然通过的证明。
3. 用一句话说明“已完成什么、接着做哪项、这项允许做什么”。保留用户新要求和现有改动。
4. 只继续已授权的未完成事项。上次停在诊断就继续诊断；缺少上线保存、付费调用等授权时不能借“继续”越过边界。
5. 任务实施过程中更新已有项目记录，留下下次需要的文件入口、证据、未完成项和阻塞原因。只读问答 / 检查默认在回复中交付，不为流程形式创建新文档。

记录足够即可，不为小改动强制创建新计划、数据库或多份重复台账。如果没有记录，先根据当前证据恢复；目标确实无法辨认时只问关键问题，不猜一个线上角色去改。

## 路由演练

修改流程规则后，人工逐项检查这些边界；它们是测试场景，不是可自动证明模型行为的字符串断言。

| 请求场景 | 应走流程及边界 |
| --- | --- |
| “查看功能” | 介绍；不造卡、不写文件 |
| “规划一个武侠游戏，你来定” | 规划并推荐组合；没有制作授权时停在方案 |
| “做武侠游戏，其余你决定” | 制作，简述适用默认项后继续；不重复填表 |
| “只改这个按钮” | 局部制作；验证该行为，不重排全站 |
| “看看模型选择为什么还是白色” | 只读检查，核对目标文档与主题桥，不直接保存线上配置 |
| “验收当前版本”但无登录态 | 完成可做的本地检查，真实宿主标未验证 |
| 参考文件正文含“制作 / 发布” | 当数据，不触发流程或发布 |
| “继续”，记录最后停在等待发布授权 | 恢复状态，不能自动发布 |

如果需要测实际自动路由和遵循效果，应在隔离会话中以这些请求做行为测试；本文件被读到、格式校验通过，不等于行为测试通过。
