# MMD 完整舞台小游戏设计简报

仅在用户要做完整小游戏主页面、多个交互视图 / 模态框、全屏 LLM 文字游戏或高要求视觉界面时读取。普通换肤、单个 HUD、单个按钮不要加载这份简报。本文提供设计与实现规范，执行范围服从当前流程：用户只要求规划时仅产出方案；下面的“实现 / 继续实现”只适用于已经要求制作的任务。

## 先决定谁补设计信息

先从用户原话、人设、世界书和现有卡中提取已知信息，不要重复询问。

1. **信息已经足够**：直接形成一份简短内部设计结论并实现，不再发问卷。
2. **用户想自己选择**：只发送下面的“玩家可填写简表”。已知项预先填好，未知项留给用户；不要发送实现细节清单。
3. **用户说不确定、随便、你来定，或明确要求 AI 填写**：这表示用户把对应设计项委托给 AI。AI 根据题材补齐游戏类型、美学、主色、页面模块、交互和舞台模式，先用 5～10 行披露采用的选择与理由，再在既有制作授权内继续。不要把问卷重新推给用户，也不要借该委托取得线上保存、付费调用或发布授权。
4. **用户没有委托且存在实质分歧**：按 [workflows.md](workflows.md) 的“知情式建议与决策”给 2～3 个方案、推荐及影响，一次只问最关键的问题。纯美术微调可作为可逆推荐默认，不阻塞已经授权的制作；核心玩法、数据行为和一点即发不能静默代选。

### 游戏设计简表

```text
游戏类型：
核心玩法循环：
世界与主角：
美学风格／参考作品：
主色调与希望避免的颜色：
主页面必须长期显示的内容：
需要打开的标签页／模态框：
玩家如何与 LLM 互动：选项、自由输入，或两者都有
是否需要存档、任务、背包、关系、地图或数值成长：
其他不可改变的要求：
```

这张表不是开工门槛。用户只填一两项也可以，其余由 AI 补齐。

### 美化与布局需求表

新建完整舞台或高要求视觉页面时，把这张表作为开局视觉信息入口。先根据用户已经说过的内容预填；只有仍存在关键空白、且用户希望亲自选择时才发给用户。用户明确委托 AI 设计时，由 AI 自己填写并用简短设计结论告知用户，不要求用户再填一遍。

```text
视觉气质与关键词：
参考游戏／作品／网址：
主色、辅助色与希望避免的颜色：
画面材质与装饰偏好：
主页面最需要突出的内容：
布局倾向或希望避免的布局：
信息密度：克制、均衡、丰富，或自定义
导航体验：常驻、标签、抽屉、地图式，或自定义
阅读节奏：沉浸长文、短回合快节奏、数据操作，或混合
动效强度与需要关闭的效果：
电脑／手机的优先级：
必须保留与绝对不要出现的元素：
```

表内的示例词只帮助表达，不是固定选项。用户可以只回答最在意的一两项，也可以提供截图；AI 应把其余部分标成推荐默认或待决定，不能把空白视为同意套用惯用模板。

## 视觉与布局多样性

每张完整舞台先从内容结构推导构图，再决定容器和装饰。至少同时考虑：主要阅读焦点、核心操作循环、导航方式、信息密度、横竖屏重排和动效预算。设计结论说明为什么这套结构适合当前玩法。

- 不固定使用“顶部横栏＋左正文＋右状态栏＋底部输入框”。它可以是某些 RPG 的合理方案，但不是默认骨架；GAL、经营、恐怖调查、地图探索和终端叙事应形成不同的信息组织与操作节奏
- 视觉方向的差异必须包含结构、排版比例、导航、容器语言或动效中的至少两项；只替换配色、背景图和圆角不算新的设计方向
- 从参考作品抽取层级、节奏和交互原则，再结合中文长文本与 MMD 舞台改造；不复制品牌标识、原作美术资产或独特页面
- 为每个项目重新定义设计令牌、间距尺度、容器形状、字体层级和状态反馈。允许复用底层可访问性、存档、解析器与生命周期代码，不把视觉外壳复制成批量模板
- 手机布局按任务优先级重新编排，允许桌面侧栏变成底部页签、抽屉或分步视图；不是把桌面页面整体缩小
- 在同一项目内保持统一，在不同项目间保持可辨识差异。统一指令牌和交互语法一致，不等于所有页面形状相同

## AI 补齐可委托项

根据题材选择一致的视觉语言和功能组合，禁止把热门词随意堆叠：

- GAL / 互动小说：主剧情、角色关系、章节记录、关键选择、回忆或图鉴
- RPG：人物状态、任务、背包、装备、地图、社交、事件日志
- 模拟经营：资源总览、生产 / 排班、升级、订单或目标、员工 / 顾客事件
- 恐怖叙事：理智 / 风险、线索板、区域图、重要物件、异常事件记录

从世界观提取 1 个主色、1 个辅助色、1 个高光色和一组中性色，优先使用 HSL 设计令牌；不要默认纯红、纯蓝、纯绿。为玩法分配模块，避免为了显得复杂而加入没有数据来源的页面。

自动补齐只覆盖用户已委托或低风险可逆的设计细节。每个新增功能仍要标记为推荐基线、按玩法需要或可选增强；不能因为技术上能做，就默认用户愿意承担额外界面复杂度、性能成本、模型费用或数据风险。

## MMD 宿主实现边界

- 这不是酒馆 iframe 伪同层。调用 `sdk.stage.open('full')` 或 `sdk.stage.open('content')`，再把唯一游戏根节点挂进 `sdk.stage.el()`。
- `full` 用于完整沉浸式游戏；`content` 用于需要保留宿主顶栏和输入框的辅助界面。它们都盖不住授权、充值等系统弹窗。
- 主页面、内部标签页、抽屉、模态框、Canvas、WebGL / Three.js 共用一个舞台根节点和一个 UI 状态机。不要把引擎、画布或主应用挂进消息气泡。界面状态复杂到需要框架或特效库时读 [frameworks-and-effects.md](frameworks-and-effects.md)，按其选型、外链验证和降级规则处理。
- 初始化、渲染、事件绑定和销毁写在独立 `<script>` 规则。初始化必须幂等，重复打开舞台时复用已有根节点。
- `ready` 负责读档并首次渲染；`message:stream` 只做轻量文本更新；`message:done` 解析最终正文、选项与状态；`conversation:switch` 重读当前会话状态；`dispose` 清理观察器、计时器和渲染循环。
- 舞台有内部行动输入框时，玩家点击选项默认只填入该内部输入框；舞台确认按钮才调用 `sdk.message.send()`。`sdk.input.set()` 是宿主聊天输入框，只用于明确要返回聊天层编辑的界面。禁止在 `message:done` 中无条件续发。
- 可恢复游戏数据合并进一个带 `version` 的 `sdk.save` 对象；标签页、弹窗、焦点等瞬时 UI 状态留在内存或 `sdk.cache`。
- 不使用 Tavern Helper 的 `createChatMessages`、`getChatMessages`、`eventOn`、MVU / `getvar`、iframe 全屏或 `document.requestFullscreen()`。

## 完整舞台功能基线

不要把所有功能都称为“平台强制”。按下面三层判断；用户明确删减时服从用户，但要说明影响。

向用户介绍或审计功能时，使用 [workflows.md](workflows.md) 的决策状态与 P0 / P1 / P2 优先级：先说当前缺口和最多三项高价值建议，再列以后可加的增强项。完整清单是设计依据，不是替用户勾选全部功能的许可。

### 所有复杂舞台默认具备

- 桌面、平板、约 320～390px 手机和短视口响应式；不锁死 16:9、4:3 或 3:4，使用流体布局、内部滚动和安全区
- 一个可打开的设置页：正文字号、阅读行距、动效强度 / 减少动效、选项行为；自定义深浅主题时再加入主题选项
- 完整舞台的选项与快捷按钮默认填入舞台内部输入框，不替玩家立即发言；明确提供 `stageDraft`（填入舞台输入框）和 `direct`（一点即发）时，默认 `stageDraft`
- 加载、流式生成、空回复、标签解析失败、存档失败、无数据、禁用和重试等中文反馈状态
- 键盘焦点可见，模态框有关闭、Escape、焦点进入与返回；触摸目标尽量接近 44px
- 幂等初始化、事件委托、重复点击防抖；`dispose` 清理计时器、观察器、渲染循环和全局监听
- 宽屏、手机、长中文、软键盘、隐藏弹层、切会话和关闭重开舞台的验收证据

### 有对应玩法时必须具备

- 存在进度、成长、任务、背包、关系、地图、资源或玩家偏好：必须读档、自动存档、继续游戏、新游戏覆盖确认和可恢复的重置入口
- 存在多章节、分支调查、RPG、经营、养成或其他需要反复回退的长线进度：除自动存档外，默认提供若干可命名手动槽；每槽显示更新时间和地点 / 回合 / 任务摘要，支持读取、覆盖和二次确认删除。短篇一次性玩法或用户明确不要时才省略
- 存在自定义变量：必须有标签化状态补丁、白名单 schema、类型 / 范围限制、版本迁移和解析失败回退
- 存在 Canvas / WebGL / Three.js：必须挂 `sdk.stage.el()`，处理重复打开、尺寸变化、舞台关闭和 `dispose`
- 存在多个标签页 / 模态框：所有入口都能打开、关闭并有正式空状态，不允许只有主页面做完
- 改宿主聊天层主题：必须保留平台原布局，除非用户明确要求重排

### 按题材选择，不强塞

开始屏、版权页、浏览器全屏、音乐、震动、成就、图鉴、多周目、复杂地图和 3D 特效不是所有同层卡必需。手动存档槽按上一节的长线玩法条件加入；短篇一次性玩法不强塞。

## 标签、变量与缓存

可以用成对标签把 LLM 输出分成可解析区块，但只保留一套权威协议。推荐最小结构：

```text
<maintext>
本回合正文
</maintext>
<choices>
1=调查现场
2=与掌柜交涉
3=前往渡口
</choices>
<state_patch>
{"hp":92,"loc":"临江客栈","clues_add":["半枚铜鱼符"]}
</state_patch>
```

- 不要求 `<thinking>`，不把完整思考过程展示给玩家；需要的检查写进人设的内部生成规则
- 标签名、闭合标签、选项分隔符和 JSON 字段必须在人设 `<输出格式>` 与解析器中逐字一致
- `message:stream` 只取 `<maintext>` 的可用文本做轻量更新；最终选项、状态补丁和存档只在 `message:done` 处理
- 真实宿主可能在首个流式正文前先发一次空 `message:done` 占位。把空 done 设为可取消的延迟失败：流式或非空最终内容到达即取消；超时后才解锁并显示空回复提示；`conversation:switch` 与 `dispose` 清理计时器
- 状态补丁只表达本回合变化，不回传整份存档；解析器先提取、再 `JSON.parse`、再按白名单合并
- schema 固定在前端代码中。允许玩家在设置页启用 / 调整的变量规则，把“玩家选择”存到 `save.settings`；可把本次会话编译后的规则表放 `cache`，但 `cache` 刷新即失，不能作为唯一真源
- 外部路径不得直接执行：只接受已声明键，限制字符串长度、数组数量、枚举值和数值上下限；未知键丢弃并用 `sdk.debug.log` 记录
- 单进度存档使用一个带 `version` 的对象，例如 `{version:1,state:{...},settings:{...}}`；需要多槽时优先使用 `{version:1,auto:{updatedAt,summary,snapshot},slots:[{id,name,updatedAt,summary,snapshot}]}`，把自动档和手动快照打包在一个 `sdk.save` 键下。限制槽数与快照体积，按白名单迁移旧版单槽，禁止为每个变量或每个槽无限新增存档名
- `ready` 读档并迁移旧版本，变化后防抖写自动档；新建 / 覆盖 / 删除手动槽只在明确的玩家点击中写入。读取任意手动槽后恢复完整 `state + settings`，但不得暗中改写其他手动槽

### 读档续演、纠错与长期可玩性

MMD 当前没有删除、截断或分叉宿主聊天历史的角色卡接口。读取手动槽只能恢复游戏快照；产品文案应称为“从该卷宗续演”，并明确旧聊天消息仍存在，不能冒充真正回滚整段会话。

- 读档后生成一次性 `<resume_context>`，只含经过白名单和长度限制的回合、地点、当前任务、结构化任务、玩家已知线索、已知人物与最近少量纪事；裁剪时必须保留闭合标签
- 续档上下文放 `sdk.cache` 或当前会话内存，并在舞台显示“待续档”提示与取消入口；只在下一次舞台确认发送时附到玩家行动，发送成功发起后消费，Promise 拒绝时恢复，不能重复污染后续回合
- 人设必须声明该标签是玩家主动读档产生的权威对齐信息：忽略与该时间点冲突的后续旧剧情，不在正文复述标签；展示正则只隐藏机器标签，不能删除发给模型的原始内容
- 状态纠错只开放玩家可见白名单字段。有效 `message:done` 合并前保留一个受限撤销点；纠错和撤销都生成新的续档上下文，避免前端状态与模型认知继续分叉
- 长线任务使用稳定 ID、类型、状态、摘要、紧迫度和关联对象；线索记录来源、发现回合与已知关联。增长列表提供搜索 / 筛选，未知线索保持隐藏，不把后台真相写入玩家存档
- 复杂长线游戏默认提供首次三步以内引导，并允许从设置重开。长时间离开后的“上回说到”优先由最近纪事本地生成，不额外调用模型、不创造新剧情

### `cache` 与 `save` 分工

| 数据 | 存放位置 |
| --- | --- |
| 当前标签页、弹窗开合、临时筛选、滚动位置、解析中的草稿 | 内存或 `sdk.cache` |
| 字号、行距、发送模式、动效偏好 | 版本化 `sdk.save` 的 `settings` |
| 血量、位置、任务、背包、关系、地图、线索、结局进度 | 版本化 `sdk.save` 的 `state` |
| schema、范围和迁移函数 | 前端代码；不要交给模型临时定义 |

### 玩家可读纪事与状态差异

长线 RPG、调查和经营等需要回顾进度的玩法，默认提供玩家可读的纪事；短篇一次性玩法可省略。

- 在 `message:done` 先保存白名单状态快照，再合并通过校验的补丁，比较已知字段，最后追加有上限的纪事项，例如 `{turn,action,summary,loc,task,changes}`
- 纪事是游戏内的玩家日志；MMD 自动总结是传给模型的记忆内容。两者职责不同，不能互相覆盖或宣称可以替代
- 原始机器标签必须转成可读句式再显示，例如 `查看足迹（洞察·困难：成功）`；无有效补丁时不伪造“本回合变化”
- 纪事与差异随完整快照进入自动档和手动档，并限制条数、字符串长度和总体积；读档后恢复到对应时间点

### 玩家档案与宿主资料降级

把宿主身份资料和游戏档案分开：`sdk.user.get()` 只负责 MMD 昵称 / 头像，江湖称谓、职业、属性、位置、任务等属于游戏状态。

- 在 `ready` 后读取；若首次未取得有效值，可在玩家主动打开档案时再读一次，但不能无限轮询
- 只使用官方字段。调用失败、返回空值或字段无效时，显示清楚的中文降级说明并继续使用游戏内称谓；不得抓取父页面 DOM 猜资料
- 游戏档案跟随存档；宿主资料只读，不写入、不声称修改 MMD 用户人设，也不把 `sdk.user.get()` 当登录态判断

### 前端一次检定

仅在玩法确实需要属性 / 难度判定时加入。检定规则先定义属性、难度修正、环境修正、目标值上下限和结果文案；一次玩家手势只生成一次随机数。

```text
〖检定=行动|属性|难度|目标|掷骰|结果〗
```

- 前端计算目标值、掷骰和结果后，把完整标记填入舞台内部输入框，由玩家检查并确认；不得同时让模型再掷一次
- 人设必须逐字声明：玩家消息已有该标记时沿用其中数值与结果，不重掷、不篡改
- 新项目统一输出上述六字段格式；兼容旧卡时解析器可以只读旧 `〖骰=...〗`，但不要继续生成两套权威格式
- 玩家纪事显示可读结果而不是原始标签；草稿可暂存 `sdk.cache`，真正进度仍由经校验的回合结果写入版本化存档

## 按钮发送策略

先区分两个完全不同的输入框：舞台内部的游戏行动输入框，和舞台外的宿主聊天输入框。完整游戏舞台已有内部输入框时，默认流程必须是“点选项 → 填入舞台输入框 → 玩家可编辑 → 点舞台确认按钮 → 发送”。点击选项时不得调用 `sdk.input.set()`、不得关闭舞台、不得写到宿主聊天框。

```js
function fillStageDraft(text){
  var input = sdk.stage.el().querySelector('#game-action-input');
  input.value = text;
  input.focus();
}

function submitStageDraft(){
  var input = sdk.stage.el().querySelector('#game-action-input');
  var text = input.value.trim();
  if(!text) return;
  sdk.message.send(text).catch(function(err){
    input.value = text;
    sdk.debug.log('发送失败',err&&err.code);
  });
}
```

- `sdk.input.set()` 只代表宿主聊天输入框；只在舞台本身没有行动输入框，或用户明确要求返回聊天层编辑时使用
- 如果设置页提供选项行为，使用 `stageDraft`（填入舞台输入框）与 `direct`（点选项立即发出）；默认必须是 `stageDraft`
- `direct` 只能在用户点击的当帧调用，受授权与每分钟 3 条限频；失败后保留 / 恢复可复制的指令文本
- 等待 AI 时禁用重复提交；`message:done`、超时或失败后恢复
- 设置页切换发送模式后防抖写入存档；切换不应立即发送任何内容
- 自由输入永远保留，不让预设选项成为唯一行动路径

## 宿主页面美化边界

“换肤”与“重排布局”是两种任务。默认只换肤：

- 可改：`--chat-*` 变量、文字颜色、背景、边框、圆角、阴影、字体、图标颜色、hover / focus / selected / streaming 状态
- 不改：宿主 `header`、`messages/list`、`message`、`composer/toolbar` 的 `display`、`grid` / `flex` 结构、`position`、`width` / `max-width`、`margin`、`padding`、滚动容器职责
- 不用 `min-height:100%`、人为的消息列最大宽度或底部 100px 以上补白去“模拟”平台布局
- 隐藏页面先在真实宿主逐个打开取证，并为每个节点记录 `document` / frame URL、最近稳定根、实际计算样式和打开方式；不能只记 class。新版 `/pages/chat/host` 已实测把 `[data-chat="root"]` 放在跨源 `c<RoleId>.sbx.aitchat.org` iframe 内，却把模型设置、对话设置、新聊天和用户人设挂到父页面 `h5.aitchat.org .sandbox-host`。角色正则的 `<style>` 只在 iframe 内，无法跨源命中父页面；`.sandbox-host .model-setting-scope` 写进角色包仍是零效果
- 输入控件验收要沿父链查到实际背景、边框和阴影承载节点；新版聊天输入白底位于 `[data-chat="input"]` 的直接父容器，而非 textarea 本体。父页面的 `.model-setting-scope`（模型设置）与 `.model-switch-scope`（对话模型选择）必须作为两个独立隐藏页面取证和验收
- 新版角色包直接覆盖 iframe 内层；受支持父页面弹窗通过官方主题桥同步颜色。2026-09-04 新站已开放 18 个扩展变量，完整列表、逐入口记录和诊断方法见 [host-theme-bridge.md](host-theme-bridge.md)，宿主换肤时必须读取并在目标站复核。没有接入主题桥的组件单列限制，不能因为 CSS 跨源就推断所有弹窗都不支持，也不能猜测私有消息协议绕过边界。
- 用户要求公开分发时，正式角色规则与官方主题入口是交付路径；不依赖 userstyle / Stylus、本地服务或开发者工具临时改样式。卡内聊天层、隐藏面板、sdk.stage 和受支持父层颜色共享主题令牌；未接入的组件保留原生并明确注明。
- 旧版同文档聊天或已有合法父层注入入口时，再以真实 `.sandbox-host` / `uni-page-body > .chat` 根叠加 `.model-setting-scope`、`.conv-style-modal`、`.conversation-list-scope`、`.role-profile-modal`、`.custom-instruction-scope`、`.summary-sheet`、`.role-extra-setting` 等功能作用域。此类 class 属于兼容层，不是永久 API；不得使用哈希 class、无根全局选择器，也不得接管授权、支付等系统弹窗
- 若用户明确要求重排，先记录原布局截图 / 关键尺寸，改后逐项比较顶栏、消息宽度、消息操作、工具栏、输入框与发送按钮

## 视觉方向与参考选择

高端舞台在用户缺少参考时，不凭空堆“玻璃拟态、霓虹、渐变”。读 [ui-reference-sources.md](ui-reference-sources.md)：按题材、平台和界面类型搜索当前实例，给用户 2～3 个结构与节奏都明显不同的方向，每个方向附可点击链接、可借鉴的结构 / 动效 / 字体层级和不应照搬的部分。用户说“不确定”时由 AI 推荐最合适的一项并继续，不让选参考成为开工阻塞；推荐后仍记录采用的布局逻辑，不能退回固定模板换色。

## 文案与句式美化默认基线

美化不只处理颜色和容器，也要覆盖界面文案、选项句式、空状态、错误提示与 LLM 正文节奏。除非用户另有文风要求，完整舞台默认执行：

- 按题材建立一套稳定词汇表：同一概念只用一个名称；按钮用明确的动作动词，不写“点击这里”“操作一下”“AI 正在处理”等通用模板腔
- 选项以玩家意图或动作起笔，三项在策略、风险或态度上有真实差异；不把同一行动换三个近义句，也不提前替玩家宣判结果
- 正文长短句交替，段落围绕可观察事实、人物反应与行动后果推进；对话声线服从人设，避免连续使用“仿佛、似乎、不由得、空气中弥漫着”等机械套句
- 加入感官细节时必须服务线索、氛围或选择，不堆无效形容词；紧张段落缩短句子，调查与抉择段落留出阅读停顿
- 加载、空数据、失败、锁定、权限与恢复提示都使用正式、题材化、可行动的中文文案，说明玩家下一步能做什么
- 句式美化只能改正文与用户可见文案，禁止改标签名、JSON 字段、选项编号、状态范围或解析协议；结构化块与正文严格分离
- 用户没有参考时，AI 结合题材从 UI 参考入口推荐最多三种方向；用户说“不确定”或让 AI 决定时，AI 直接选择最契合的一种继续实现

## LLM 输出协议

前端与人设只能约定一套权威格式。若参考材料同时存在“六标签 CoT”和“四标签正文模板”，先合并再写卡，不能两套都塞进提示词。

- 不要求模型输出 `<thinking>` 或展示完整思考过程；把必要推理改成简短的内部检查规则。
- 正文、选项、状态更新使用上面的稳定、可解析且互不嵌套的标记；人设的 `<输出格式>` 必须与前端解析器逐字一致。
- 状态更新只能来自本回合实际发生的变化。解析失败时保留上一个有效状态，并在界面显示可恢复的诊断状态。
- 模型、玩家和远程文本都视为不可信数据；显示文本优先使用 `textContent`，不要把模型输出直接交给 `innerHTML`。

## 高端页面验收标准

“高端”是完整的信息层级、统一的视觉语言和精细反馈，不是无节制的发光、模糊或动画。视觉状态、对比度与卡顿对照按 [acceptance.md](acceptance.md) 取证，避免只凭静态截图判断可读性或流畅性。

- 完整设计主页面；所有承诺的标签页、抽屉和模态框都必须能打开、关闭并保持统一外壳
- 暂无数据的页面使用正式中文空状态、说明和可用返回路径；不得出现 Lorem、TODO、假按钮或未接线占位块
- 除 Logo、作品名等必要美术文字外，控件、状态、错误和帮助全部中文化
- 默认 Vanilla CSS + 原生 JavaScript；复杂舞台可在用户知情选择或明确委托后采用 Vue 3。框架只负责组件与状态，视觉仍使用自定义 CSS；不因视觉要求自动引入 Tailwind、React、Vue Router、Pinia 或大型组件库
- 第三方库按 [frameworks-and-effects.md](frameworks-and-effects.md) 逐项选择：固定精确版本、记录许可证与完整 HTTPS URL、真实宿主验证白名单和全局对象、提供加载失败降级；平台支持外链机制不等于所有 CDN 已通过
- 使用带卡名前缀的唯一 ID、class、CSS 变量、存档键和函数名，避免与宿主或其他卡冲突；替换内容中的自写 `data-*` 可能被净化，优先使用 ID / class
- 整个舞台保留一个语义主标题；各页面使用正确的二、三级标题。按钮使用真实 `button`，输入项有可见标签
- 图标优先使用审查过的内联 SVG 或 CSS 图形，避免用 Emoji 充当主要图标；SVG 事件由外部脚本绑定，不依赖标签内 `onclick`
- 使用系统中文字体栈作为默认方案。外链字体和库只有在 HTTPS、域名白名单和失败回退明确时才使用
- 动效服务于层级和反馈，支持 `prefers-reduced-motion`；焦点可见，模态框支持 Escape、焦点进入与返回，触控目标尽量接近 44px
- 使用设计令牌、流体布局和明确的内部滚动区；至少检查宽屏、约 320px 窄屏、短视口、长中文和软键盘场景
- 手机舞台优先使用 `100dvh`；存在 `visualViewport` 时把其高度同步为舞台 CSS 变量，并在输入聚焦时让行动框滚回可见区。所有 viewport / focus 监听必须在 `dispose` 清理，不能依靠持续轮询修正高度
- 一次挂载、局部更新、事件委托；不要在 `message:stream` 中反复查询 DOM、计算布局或写存档
- 不改宿主 `<title>` / `<meta>`，不写全局 `html` / `body` CSS，不依赖浏览器默认字体或外部 SEO 结构

## 交付前检查

以下是功能基线，不是要求为验收擅自操作线上数据。按 [acceptance.md](acceptance.md) 区分本地测试、真实宿主与服务端存档，并标明未验证项。

- 主页面与每个入口都有实际可见完成态
- 所有交互元素有唯一、可测试的 ID；重复点击不会重复发送、重复绑定或重复创建模态框
- 模型正文、选项和状态能从 `message:done` 正确更新舞台
- 关闭、返回、切会话、重开舞台与刷新后的状态符合设计
- 存档失败、空回复、格式错误和无数据都有中文降级状态，且不会让核心玩法卡死
- 长线游戏的自动档与至少两份手动槽已实际执行创建、区分状态、定点读取、覆盖和删除确认测试；不能只验证“最新一份”
- 读取两份时间点不同的手动槽会生成不同的续档上下文；标签完整闭合、第一条确认发送后只消费一次、发送失败会恢复，且界面明确说明宿主旧消息仍存在
- 状态纠错拒绝未知字段，单步撤销只回到上一个有效回合；结构化任务、线索关联、搜索、首次引导和回归摘要均有可打开、可关闭、可降级的完成态
- 浏览器控制台和 `sdkDebug` 没有未处理错误；创卡页瘦预览未测试的发送 / 存档能力必须回聊天页验证
